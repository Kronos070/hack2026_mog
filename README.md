# Воздушный Шар — состояние проекта

Бонусная crash-игра для «Столото». Репозиторий состоит из двух частей:

- `backend/` — Quarkus + PostgreSQL, реальный сервер
- `frontend/` — Vite + React, сейчас работает на встроенном моке

Документ описывает, **что уже есть на бэкенде, чего не хватает фронту и где контракты расходятся**.

---

## 1. Что уже готово на бэкенде

| Область | Эндпоинт | Статус |
|---|---|---|
| Авторизация | `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` | Готово |
| Профиль | `GET/PUT/DELETE /api/users/me`, `PUT /api/users/me/password` | Готово |
| Пользователи | `GET /api/users`, `GET /api/users/{id}` | Готово |
| Старт раунда | `POST /api/game/start` | Готово |
| Cashout | `POST /api/game/cashout` | Готово |
| Состояние раунда | `GET /api/game/state?roundId=` | Готово |
| История | `GET /api/game/history` | Готово |
| Пополнение баланса | `POST /api/game/top-up` | Готово |
| House edge | `GET /api/game/house-edge`, `POST /api/game/house-edge/reset` | Готово |
| Real-time | WebSocket `/ws/game` (TICK, BOOSTER_ACTIVATED, CASHOUT, CRASHED) | Готово |

Схема БД (`V1.0.0__initial_schema.sql`) уже содержит `users`, `game_rounds`,
`game_configs`, `tournament_entries`.

**Отдельно отмечу:** бэкенд правильно **не отдаёт `crashMultiplier` при старте** —
только при cashout. Плюс реализован provably fair (`provablyFairHash`, `serverSeed`,
`clientSeed`, `nonce`). Это снимает главный риск честности, который был в прототипе.

## 2. Чего не хватает для подключения фронта

### 2.1. Критично — без этого не работают обязательные сценарии ТЗ

**Конфигурация игры (админка).** Таблица `game_configs` есть, но нет ни эндпоинта,
ни сервиса. По ТЗ (§1.9) это **обязательный модуль**: эксперт должен менять
`points_per_line` и сразу видеть эффект.

```
GET  /api/admin/config    → текущие параметры
PUT  /api/admin/config    → сохранение (только роль admin)
```

Набор параметров, который ожидает фронт, — в таблице раздела 4.

**Роли.** В `UserProfileResponse` поле `role` есть, но непонятно, как пользователь
становится админом. Нужен либо seed-пользователь с ролью `ADMIN`, либо эндпоинт
назначения роли. Фронт закрывает `/admin` по `role === 'admin'`.

**Завершение раунда.** Сейчас есть `cashout`, но нет способа узнать итоги раунда,
**если игрок не забрал выигрыш** (ставка сгорела). Фронту нужны: заработанные очки,
пройденные уровни, выданная награда. Варианты: отдавать это в `CRASHED`-сообщении
WebSocket или добавить `GET /api/game/result?roundId=`.

### 2.2. Важно — заявлено в ТЗ как дополнительное, у фронта уже есть UI

**Турнирная таблица.** Таблица `tournament_entries` в БД есть, эндпоинта нет.

```
GET /api/tournament              → { title, endsAt, entries[], currentPlayerId }
GET /api/tournament/leaderboard  → [{ playerId, playerName, points }]
```

Фронт опрашивает рейтинг раз в секунду (ТЗ допускает polling ≤1 сек).

**Игровые очки.** В `game_rounds` есть `points_earned`, но в профиле пользователя
очков нет — только `bonusBalance`. Фронт показывает очки в рейтинге и профиле.
Нужно поле `points` (сумма) в `UserProfileResponse` или отдельный эндпоинт.

### 2.3. Реализовано на фронте как мок — бэкенда нет вообще

Это то, что я сделал целиком на фронте. Если решите переносить на сервер — вот что нужно:

| Механика | Что требуется |
|---|---|
| **Достижения** (10 шт.) | Таблица `user_achievements`, выдача при завершении раунда, `GET /api/users/me/achievements` |
| **Ранги** | Расчёт по чистой прибыли (выплаты − ставки), 6 уровней |
| **Коллекция наград** | Таблица прогресса, выдача фрагмента за раунд (ТЗ §1.5 — **обязательно**) |
| **Расширенный профиль** | Статистика: сыграно раундов, побед, лучший коэффициент, сумма ставок |

Схемы этих сущностей — в [frontend/src/shared/api/contract.ts](frontend/src/shared/api/contract.ts)
(`achievementSchema`, `rankSchema`, `profileSchema`).

## 3. Расхождения контрактов

Фронт писался против придуманного контракта, пока бэкенда не было. Ниже — где они
не совпадают. **Приводить будем фронт к бэкенду**, но список нужен, чтобы ничего не потерять.

### 3.1. Пути

| Фронт ожидает | Бэкенд отдаёт |
|---|---|
| `POST /rounds` | `POST /api/game/start` |
| `POST /rounds/cashout` | `POST /api/game/cashout` |
| `POST /rounds/finish` | — (нет) |
| `GET /rounds/history` | `GET /api/game/history` |

### 3.2. Старт раунда

Фронт шлёт `{ theme, cost, boosterTier }`, бэкенд ждёт `{ betAmount, theme, boosterMultiplier }`.

Разница по существу: у фронта **тир бустера** (1–4), который индексирует множители из
конфига; у бэкенда — **сам множитель**. Нужно договориться, где лежит таблица множителей.

Тема: фронт использует `green` / `red` (9 и 12 уровней по ТЗ), бэкенд по умолчанию
подставляет `classic`. Нужно согласовать допустимые значения.

### 3.3. Идентификаторы

- Фронт: `id` пользователя — строка, раунд — строка
- Бэкенд: `id` — `Long`, раунд — `UUID`

Фронт поправлю, вопросов нет.

### 3.4. Профиль

| Фронт | Бэкенд |
|---|---|
| `name` | `username` |
| `balance` | `bonusBalance` |
| `points` | — (нет) |
| `role: 'user' \| 'admin'` | `role: String` |

### 3.5. Авторизация

Фронт сейчас не имеет экранов входа — вместо них выбор «игрок / админ» (заглушка).
Бэкенд ждёт настоящие `login` / `password` и отдаёт Bearer-токен
(`AuthResponse { token, tokenType, expiresIn, user }`).

Нужно: экраны входа и регистрации, хранение токена, перехватчик для заголовка
`Authorization`. Это работа на стороне фронта.

## 4. Параметры конфигурации, которые ждёт фронт

Что сейчас лежит в `game_configs` (seed) и что нужно фронту — не совпадает.

| Параметр | Описание | Есть в seed |
|---|---|---|
| `alpha` | Крутизна распределения краха | нет |
| `maxMultiplier` | Верхняя граница коэффициента | да |
| `minCrashMultiplier` | Минимальный коэффициент краха | да |
| `multiplierGrowthRate` | Темп роста | да (но значение 1.05 — другая формула) |
| `growthAcceleration` | Разгон кривой: 1 — ровно, 2 — резко | нет |
| `pointsPerLine` | Очки за уровень | да |
| `pointsCashoutBonus` | Очки за cashout | да |
| `pointsBoosterBonus` | Очки за бустер | нет |
| `boosterTierValues` | Множители бустеров x1–x4 | нет |
| `lootProbabilities` | Вероятности уровня бустера по темам | нет |
| `minWinAmount` | Порог для апсейла | да |
| `popupTimeout` | Автозакрытие попапа | да |

### Про формулу роста

Фронт использует экспоненту **с разгоном**:

```
multiplier(t) = e^(growth_rate · t^acceleration)
```

При `acceleration = 1.5` начало полёта пологое (~x1.11 за первую секунду), дальше
кривая круче обычной экспоненты (x2.23 на 4-й секунде, x9.61 на 8-й). Подобрано так,
чтобы игрок успевал нажать «Забрать»: средний раунд ~4.5 сек, короче 2 сек — лишь ~3%.

Если на бэкенде формула другая (`growth_rate: 1.05` в seed намекает на это) — нужно
свериться, иначе анимация на клиенте разойдётся с серверным расчётом.

## 5. Что делает фронт сейчас

Работает на моке в `localStorage`, полностью автономно. Переключение на реальный бэк:

```bash
VITE_API_MODE=real VITE_API_URL=http://localhost:8080/api npm run dev
```

Точка подмены — [frontend/src/shared/api/client.ts](frontend/src/shared/api/client.ts).
Мок-реализация рядом, в `mock-*.ts`. Подробности по фронту — в
[frontend/README.md](frontend/README.md).
